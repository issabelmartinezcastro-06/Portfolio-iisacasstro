# Multilingual sites (read only if the site has more than one language)

A pattern that worked on a Next.js 14 App Router site with English as the default and Spanish added later. Adapt names and languages to the repo; record the actual setup in `profile.md`.

## URLs

- The default language has **no prefix**, so every URL that existed before keeps working. Other languages live under `/<code>` (for example `/es`).
- Pages live in `app/[lang]/`. `middleware.ts` rewrites unprefixed paths to `/<default>/...` (the address does not change) and redirects `/<default>/...` to the unprefixed path. The matcher excludes `_next`, `assets`, `api` and any path with a dot (images, icons). A string like `".*\\..*"` must keep **two** backslashes in the file; with one, the matcher silently matches everything and unprefixed pages 404. Verify with `curl`.
- The root layout in `app/[lang]/layout.tsx` sets `<html lang>`, metadata per language and `dynamicParams = false`. File-based metadata (icons, Open Graph images) stays in `app/`.
- Relative asset URLs (`src="assets/..."`, `data-background="assets/..."`) break under `/<code>/...`. Always write them absolute (`/assets/...`).

## What to translate

Translate the chrome (navbar, mobile menu, footer, off-canvas), the home page, the listing header and the card text of every project. Long case studies and blog posts can stay in one language if the owner agrees; say so on the site. A page whose content is translated tells the layout so the translate logic knows the content language.

## Strings

- One typed dictionary per language: the default one defines the shape, the others must match it (TypeScript checks). Server components get `getDictionary(lang)` and pass pieces to sections as props; client components use a `useLocale()` context.
- Shared sections used on several pages read the dictionary through the context; page-only sections take props.
- Replace `next/link` everywhere with a small `LocaleLink` wrapper that adds the prefix. Plain `<a href="/projects/...">` becomes a `<Link>` too.
- Per-project card text for other languages lives in a separate data file (`data/projects.<code>.ts`) applied by a `localizeProject` helper. Missing text falls back to the default silently: check it when adding a project.

## Optional: translate button for untranslated content

What the owner asked for, and what was rejected:

1. A language switch in the navbar (one small button on phones). Choosing a non-default language shows a notice (in that language) saying most content is in the default language and where the translate button is.
2. A **translate button in the navbar**, not a bar above it (a bar above the navbar was rejected). First click translates the page content with the browser's on-device Translator API and shows a module explaining it; later clicks toggle the original. Where the API is missing, open Google Translate.
3. The browser remembers the visitor's language (`localStorage`). When a page's content language differs from it, a module offers to translate, with "always translate" and "not now" options. No other permanent button exists.
4. The button is hidden when the content already matches the visitor's language.
5. Mark names and terms that must not change with `data-no-translate`.

## Phone navbar

Adding controls to the navbar overflowed phones. The fix: the language switch becomes one small square button below 576 px, the brand shrinks, secondary icons hide in the middle range, and the two buttons share one square class. Always measure.

## Checks used

Routing with `curl` (`/work` 200, `/<default>/work` 308, `/<code>/work` 200, `/nope` 404), the switch and modals with headless Chrome, real translation against the Translator API, the phone navbar at 390, 360 and 320 px, a production `next build`, the linter and the type check.
